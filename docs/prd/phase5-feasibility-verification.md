# Phase 5 검증 리포트: "실제로 크롤링(수집)이 가능한가?" 재점검

> 관련 문서: [`sns-job-posting-research-prd.md`](./sns-job-posting-research-prd.md), Phase 1~4 리포트
> 실행일 기준: 2026-09-13 · 목적: 지금까지의 작업이 인스타그램/스레드/메타(페이스북)/X 채용공고 "수집(크롤링)"을 실제로 가능하게 하는지 단계별 재검증

## 1. 검증 절차 및 결과

| 단계 | 검증 내용 | 방법 | 결과 |
|---|---|---|---|
| 1 | 4개 플랫폼 키워드 검색이 되는가 | `firecrawl_search` + `includeDomains` | ✅ 4개 플랫폼 모두 결과 반환 (Phase 1~3에서 이미 확인) |
| 2 | **신뢰 큐레이션 계정을 지정한 검색이 되는가** (Phase 3 권장사항의 실증) | `firecrawl_search`로 `"designrookie.official 채용"` 검색 | ✅ 작동함 — 해당 계정의 프로필 및 게시물이 상위에 정확히 반환됨. Phase 3의 "권장"을 "검증됨"으로 격상 |
| 3 | Firecrawl 외 다른 방법(WebFetch)으로 게시물 원문에 직접 접근 가능한가 | `WebFetch`로 Instagram/X/Threads/Facebook 게시물 URL 직접 요청 | 🔴 **4개 도메인 전부 접근 차단** (`EGRESS_BLOCKED` 또는 fetch 불가) |
| 4 | 차단의 성격 확인 (도구 부재 vs 네트워크 정책) | `/root/.ccr/__agentproxy/status` 확인, README 검토 | 이 세션은 조직 정책에 따라 특정 도메인으로의 직접 아웃바운드 접속이 차단되는 프록시를 거침. Instagram/X/Facebook은 이 정책에 의해 명시적으로 차단(`EGRESS_BLOCKED`), Threads는 도구 자체가 아예 처리 불가 응답 |

## 2. 핵심 결론 (Phase 1의 설명을 정정)

Phase 1 리포트에서는 "Firecrawl 커넥터가 scrape 도구를 제공하지 않아서" 스니펫만 얻을 수 있다고 설명했다. 이번 검증으로 더 근본적인 제약이 확인됐다:

> **이 실행 환경 자체가 인스타그램·스레드·페이스북·X 4개 도메인에 대한 직접 아웃바운드 접속을 조직 정책으로 차단하고 있다.** Firecrawl MCP 검색이 동작하는 이유는 Firecrawl 서버가 이 세션의 네트워크 밖(자체 인프라)에서 크롤링을 수행하고 결과만 API로 돌려주기 때문이다. 즉 **이 환경에서 4개 SNS 플랫폼에 닿을 수 있는 유일한 통로가 Firecrawl 커넥터**이며, 이 통로가 없었다면 이번 PRD의 리서치 자체가 이 환경에서는 원천적으로 불가능했다.

**따라서 "수집(크롤링) 가능한가?"에 대한 답은:**
- **부분적으로 가능하다** — Firecrawl의 검색 API를 통한 "검색 스니펫 기반 발견"은 4개 플랫폼 모두에서 실제로 작동하며, 계정 지정 검색까지 가능해 신뢰 큐레이션 계정 위주 수집 전략(Phase 3)이 실행 가능함을 확인했다.
- **완전한 크롤링(원문 전체 수집)은 이 환경에서는 불가능하다** — Firecrawl이 제공하는 도구가 검색(search)뿐이고, 설령 원문 전체를 가져오는 별도 도구가 있다 해도 그 도구가 이 세션의 로컬 네트워크로 직접 페이지를 요청하는 방식이라면 동일하게 차단될 것이다. 원문 전체 수집이 가능하려면 **Firecrawl(또는 동급 커넥터)의 서버 사이드 scrape/crawl 기능**을 이 MCP 연동에 추가로 활성화해야 한다.

## 3. 누락되어 있던 부분 → 추가 조치

### 3.1 PRD/Phase 1 설명 정정 (완료)
"Firecrawl이 스니펫만 제공"이라는 설명을 "이 환경 자체가 4개 도메인 직접 접속을 차단하며, Firecrawl 검색이 유일한 통로"로 정정 — 아래 4장에서 본 PRD에 반영.

### 3.2 신규 액션 아이템 (Phase 4 설계에 추가)
1. **Firecrawl scrape/crawl 엔드포인트 활성화 요청**: 이 MCP 서버 설정에 `firecrawl_scrape`(또는 동급) 도구가 추가되면, 검색 스니펫이 아닌 원문 전체(정확한 마감일·전체 요건)를 서버사이드에서 가져올 수 있다. 이 활성화 여부는 이 세션에서 결정할 수 없으므로, 담당자가 Firecrawl MCP 서버 설정을 검토해야 한다.
2. **계정 지정 검색을 표준 쿼리 전략으로 채택**: Phase 3에서 식별한 신뢰 계정(디자인루키, 윤빌리티, remaincareer, owanimal, 미디어잡) + 신규 발견 계정을 대상으로 `"{계정명} 채용"` 형태 검색을 주기 실행의 기본값으로 사용 (일반 키워드 검색보다 노이즈가 현저히 낮음, 2절 검증 완료).
3. **크레딧/쿼터 관리 계획 필요**: 관측된 바 `firecrawl_search` 1회 호출당 `creditsUsed: 2`. Phase 4의 재수집 스케줄(주 1~2회 × 여러 계정/키워드 조합)을 실행하면 호출 수가 누적되므로, 운영 전환 전에 Firecrawl 요금제의 크레딧 한도 대비 예상 호출량을 산정해야 한다 (이번 PRD에서 별도로 계산하지 않음 — 후속 과제로 남김).
4. **공식 API 대안 재확인**: PRD 8장(후속 과제)의 "각 플랫폼 공식 API 연동"은 이번 검증 결과 우선순위가 높아졌다. 특히 원문 전체 수집이 필요한 경우, Meta Graph API(Instagram/Facebook)나 X API처럼 공식적으로 허용된 채널이 이 세션의 네트워크 차단과 무관하게(별도 화이트리스트 또는 서버사이드 연동으로) 동작할 가능성이 있어 검토 우선순위를 높임.

### 3.3 실시간성(최신성)에 대한 한계 인정
검색 인덱스 기반 발견 방식은 게시 시점과 검색 노출 시점 사이에 지연이 있을 수 있다는 점을 이번 세션에서 정량적으로 측정하지 못했다 (예: 게시 후 몇 시간/며칠 뒤에 검색에 노출되는지). 이는 **알려진 미검증 항목(known-unknown)**으로 남기고, 운영 단계에서 실제 게시일 대비 발견 시점을 추적해 측정할 것을 제안한다.

## 4. PRD 본문 반영 요약
- 1.3/3장/5.1장/리스크 표의 "Firecrawl 스니펫 제공" 관련 서술을 "환경의 네트워크 정책상 직접 접속 차단 + Firecrawl이 유일한 통로"로 구체화
- Phase 4 설계에 "Firecrawl scrape 활성화 요청"과 "계정 지정 검색을 표준 전략으로 채택"을 액션 아이템으로 추가
- 8장 후속 과제의 "공식 API 연동" 우선순위를 상향
